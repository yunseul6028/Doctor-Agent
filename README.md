# Doctor-Agent

**N.O.V.A. 2026** (분당서울대학교병원 의료인공지능센터 주최) **대화형 의료 진단 AI 에이전트 대회** 출품작입니다.
가상 환자에게 질문하고(ASK), 신체진찰(EXAM)과 검사(TEST)를 골라, 최종 진단(DIAGNOSE)에 도달하는 의사 에이전트를 만듭니다.

- 대회 사이트: https://nova.snubhai.org
- 평가 기준: 진단 정확도 · 정보 획득 효율성 · 임상적 안전성 (증례당 최대 60턴)
- 예선 모델: `openai/gpt-oss-20b` 고정 (파인튜닝 금지, 추론 코드에서 외부 API 호출 금지)

> 대회 요약은 [`docs/competition.md`](docs/competition.md), 설계는 [`docs/architecture.md`](docs/architecture.md)에 있습니다.

## 에이전트 구조

```
run.py ─ 증례마다 새로 시작, 결과를 한 줄씩 바로 저장, 어떤 오류에도 진단을 냄
  │
환경(가상 환자) ⇄ 진료 루프 (agent/loop.py) ─ 시간 예산 · 모델 호출 보호 (agent/runtime.py)
                     │
        ┌────────────┼──────────────────────────────┐
        ▼            ▼                              ▼
   진료 상태      행동 결정 (agent/policy.py)       근거 자료 (모두 "참고용" 힌트)
   ─ 소견 장부    1. 모델이 다음 행동 제안           ─ 주호소 26종 안전 확인 (safety/protocols.py)
   ─ 감별 장부    2. 코드가 보정                      ─ 임상 결정 규칙 12종 (knowledge/clinical_rules.py)
   ─ 대화 기록       · 문진이 진찰로 오면 문진으로    ─ 지식 베이스: 질환 12,597개 + 검사 결과 연결 452개
                     · 반복·유사 행동 차단               (knowledge/kb.py → agent/kb_hints.py)
                     · 필수 안전 확인 전 진단 시 되묻기
                  3. 진단 전 검토 (항목은 모델, 판정은 코드)
```

**핵심 설계**
| 기능 | 하는 일 |
|---|---|
| **소견 장부** | 매 턴 새 소견을 양성 / 음성 / 결과없음으로 정리. 모델에게는 긴 대화 대신 장부와 최근 4턴만 보여줌 |
| **감별 진단 장부** | 후보별 확률·지지 소견·반대 소견·상태(유력/위험/배제)를 턴마다 이어서 관리. 같은 병의 다른 표기는 하나로 합침 |
| **진단 전 검토** | 진단 직전 같은 모델이 검토의 역할로 설명 안 되는 소견·모순·확진 근거·미배제 위험 질환을 항목별로 채움. 승인/보류는 **코드가 판정**하고, 진단명 수정은 이 환자의 소견을 인용할 때만 받아들임 |
| **지침 기반 안전 확인** | 주호소 26종마다 반드시 배제할 질환과 최소 확인 항목을 출처(지침·논문)와 함께 안내. 나이·기간·조건에 맞을 때만 적용 |
| **지식 베이스 힌트** | 소견에 맞는 다른 후보, 두 후보를 가르는 특징·결정적 검사 결과, 표준 병명·질병 코드(KCD)를 참고용으로 제공 |
| **근거 인용** | 매 행동에 근거를 쓰고, 판단 기준을 쓸 때는 이름과 출처를 인용 |
| **절대 멈추지 않는 실행** | 모델 오류·시간 부족·환경 오류가 나도 증례마다 반드시 진단을 내고, 결과는 증례가 끝날 때마다 저장 |

## 기술 기반

### 1. 언어모델과 연결 방식
| 항목 | 내용 |
|---|---|
| 대회 모델 | `openai/gpt-oss-20b` (약 200억 매개변수, 전문가 혼합 구조, 답 전에 생각 과정을 출력하는 추론형 모델). 예선에서는 대회 서버의 GPU에서 실행되며 파인튜닝 불가 |
| 연결 방식 | **OpenAI 호환 채팅 API** 하나로 통일 (`llm/client.py`). 대회 서버, 로컬(Ollama·vLLM), 개발용 API(제미나이·젬마)를 코드 수정 없이 설정만으로 교체 |
| 역할별 모델 | 의사(`DOCTOR_LLM_*`), 가상 환자(`PATIENT_LLM_*`), 채점자(`JUDGE_LLM_*`), 데이터 변환(`CONVERT_LLM_*`)을 따로 지정 |
| gpt-oss 대응 | 생각 과정과 답이 섞인 응답(harmony 형식)을 정리하고, 답이 비어 있으면 생각 과정 안의 JSON을 읽음. 생각이 길어 답이 잘리면 토큰을 늘리고 추론 강도를 낮춰 1회 재시도. 서버가 지원하면 JSON 형식 강제(선택) |
| 시간 관리 | 증례당 시간 예산(`AGENT_CASE_TIME_BUDGET_S`). 60%를 넘으면 검토·되묻기를 생략하고 힌트를 줄이며, 마지막 45초는 최종 진단용으로 남김. 호출마다 제한 시간과 감시 스레드 |
| 안정성 | 재시도, 사용량 한도(429) 대기, 연속 3회 실패 시 그 증례에서 모델 호출 중단 후 최상위 감별 진단 제출. 제출 모드에서는 어떤 예외도 밖으로 나가지 않음 |

### 2. 에이전트 설계 기법
| 기법 | 적용 |
|---|---|
| **행동 반복 루프** | 관찰 → 판단 → 행동(ASK/EXAM/TEST/DIAGNOSE)을 최대 60턴 반복. 매 턴 모델은 JSON 한 줄로 소견·감별·행동·근거·확신도를 출력 |
| **구조화된 기억** | 작은 모델이 긴 대화를 놓치지 않도록 코드가 소견 장부와 감별 장부를 관리하고, 프롬프트에는 "장부 + 최근 4턴"만 제공. 프롬프트가 12,000자를 넘으면 오래된 것부터 줄임 |
| **코드가 정하는 순서** | 응답 해석 → 행동 유형 교정(문진↔진찰) → 장부 갱신 → 반복 행동 차단 → 필수 안전 확인 되묻기(1회) → 진단 전 검토(최대 2회). 자세한 순서는 [`docs/architecture.md`](docs/architecture.md) |
| **자기 검토** | 진단 직전 같은 모델을 검토의 역할로 한 번 더 호출. 모델은 정해진 항목만 채우고, 승인·보류·진단명 수정은 **코드 규칙으로 판정**. 위치 수식어("상행결장암")나 근거 없는 원인 수식어를 붙인 수정은 거절 |
| **근거 제공 (검색 증강)** | 매 턴 위험 질환 → 아직 안 한 안전 확인 → 결과가 없던 요청 → 해당되는 판단 기준 2개 → 지식 베이스 힌트 순으로 짧게 붙임. 모두 "참고용"으로 표시해 확진 근거와 구분 |
| **출력 후처리** | 생각 과정 블록 제거 후 마지막 행동 JSON 추출, 진단명에서 "~입니다" 같은 문장 꾸밈 제거, 표준 병명·KCD 코드 기록(제출 진단은 그대로) |

### 3. 의학 근거 자료
| 자료 | 내용 | 라이선스 |
|---|---|---|
| **주호소별 안전 확인 26종** | 흉통·호흡곤란·두통·급성 신경 증상·발열·복통·알레르기·실신·두근거림·객혈/만성 기침·황달·급성 관절염·요통·급성 발진·만성 가려움·부종·무월경/이상 출혈·피로·인지 저하·정신과 증상·만성 두드러기·난청·경부 종괴·출혈 경향·만성 근력 저하·영아 담즙성 구토. 확인 항목 88개, 근거 지침 43개(서지 정보를 PubMed로 확인). 항목마다 원문 확인 수준 기록(원문 34 · 2차 자료 17 · 미확인 37). 나이·기간·임신 여부 등 조건에 맞을 때만 적용 | 지침 인용 |
| **임상 결정 규칙 12종** | Wells PE, PERC, HEART, ADD-RS, qSOFA, CURB-65, Centor, Ottawa SAH, Canadian CT Head, ABCD2, Alvarado, BISAP. 원 논문의 공식을 직접 구현, 인용·DOI를 PubMed로 확인. **적용 대상 조건**(나이, 급성/만성, 외상 제외 등)을 원 논문 초록의 대상 집단에서 가져와 해당될 때만 제시 | 공식은 저작권 대상 아님, 원 논문 인용 |
| **의학 지식 베이스** | 질환 12,597개 프로필 (증상, 위험인자, 검사, 한국어 이름, KCD 코드). 5개 공개 자료: DDXPlus(CC BY 4.0), 심평원 상병마스터(공공누리 1유형), Disease Ontology(CC0), Wikidata(CC0), MedlinePlus 요약(공공 저작물) | 출처별 표기 (`data/kb/SOURCES.md`) |
| **검사 결과 ↔ 질환 연결** | 우리가 직접 작성한 표: 검사 결과 개념 262개("리파아제 상승", "AMA 양성", "CT 충수 비후" 등)와 질환 연결 452개. 연결마다 참고문헌(95개, PubMed로 확인) 또는 "교과서"(미검증) 표시. 정상 결과로 배제할 수 있는 연결 41개 | 자체 작성 |

지식 베이스는 **CPU만으로 동작**합니다 (용량 약 2.1MB, 적재 약 0.3초, 조회 약 9밀리초). 외부 라이브러리 없이 파이썬 표준 라이브러리만 씁니다. 소견 기반 후보 순위는 가중 BM25(용어 계층·같은 말 중복 제거·음성 소견 반영)에 검사 결과 점수를 더하고, 진단명은 KCD 표준 병명으로 정규화합니다.

**오프라인 성능** (LLM 없이 증례 원문에서 소견을 뽑아 정답 순위 측정, 조정에 쓰지 않은 156증례 기준): 정답이 상위 10위 안에 드는 비율 19% → **27%**, 1위 4% → 9%. 아직 힌트 수준이라 "확진 근거 아님"으로 표시해 제공합니다. 자세한 내용: [`docs/data-sources.md`](docs/data-sources.md) 7장.

### 4. 평가 방법
| 요소 | 방식 |
|---|---|
| **가상 환자** | 언어모델 환자는 증례 정보만으로 답하고 정답·해설·보강 기록은 가림. 증례에 없는 검사는 "제공되지 않음"으로 정상과 구분. 비용 없는 키워드 환자(`eval/simulator.py`)도 있음 |
| **까다로운 환자 4종** | 모호한 환자, 불안한 환자, 증상을 축소하는 환자, 기억이 흐린 환자. 여러 질문 중 첫 질문에만 답해 현실적인 난이도 부여 (`--persona mixed`로 섞어서 사용) |
| **채점** | 정확도: 언어모델 채점자(동의어·표기 차이 인정, 부분 점수) · 효율성: 사용 턴 · 안전성: 지침 기반 확인 목록 수행률 |
| **한 줄 실험 도구** | `eval/experiment.py`: 정해진 증례 묶음(smoke 5 / dev 50 / full 267)과 비교 조건(현재 코드, 지식 베이스 끔, 이전 버전)을 한 번에 실행. **실행 전 비용 추정**, 한도(모델 호출 300회) 초과 시 `--yes` 필요, 결제 오류 시 즉시 중단, 토큰 사용량 기록 |
| **비교와 보기** | 두 실행 비교(세트별 점수, 정답↔오답 뒤바뀐 증례, "결과 없음" 비율), 브라우저 뷰어(턴마다 근거·감별 후보·빠뜨린 확인), 공유용 페이지 |

### 5. 데이터 파이프라인
| 단계 | 방식 |
|---|---|
| **변환** | 객관식 문항·영어 증례를 언어모델로 대화형 한국어 증례로 변환. 원문에 없는 수치·단위가 생기면 자동 실패, 정답명 유출 검사, 한자 혼입 검사, 사람이 오역 검토 |
| **보강** | 시험 문제에서 빠진 검사 결과를 정답과 모순 없이 채움 → 전체 267증례(`data/cases_aug`). 추가 항목은 `augmented`로 표시, 진단명 직접 언급 금지 |
| **품질 검사** | `scripts/check_cases.py`(LLM 없음): 정답 누출, 원본과 보강 사이 모순, 성별·나이에 안 맞는 검사, 비현실적 수치, 검색어 문제. 반드시 0이어야 할 문제 48건 → **0건** (자동 시험으로 유지) |
| **재현성** | 변환·보강·지식 베이스 구축에 쓴 프롬프트, 모델, 날짜, 항목별 기록을 `data/labels/`에 저장. 지식 베이스는 캐시로 API 호출 없이 똑같이 다시 만들 수 있음 (대회 재현성 규칙) |

### 6. 개발 방식
- **팀 에이전트 구조**: 1명 + Claude 보조 에이전트 5종(임상 전략, 에이전트 엔지니어, 지식·검색, 평가·시뮬레이터, 규칙 준수·출시)이 역할을 나눠 병렬 개발 (`.claude/agents/`)
- 자동 시험(`pytest`) 328개, 제출 전 규칙 자동 검사(`scripts/package.py`)
- 개발 중에는 대회 모델 대신 제미나이·젬마 계열로 실험하며, 모델 교체 시 프롬프트를 다시 검증

## 빠른 시작

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env        # API 키 입력 (.env는 git에 올라가지 않음)
```

| 할 일 | 명령 |
|---|---|
| 모델 없이 동작 확인 | `python eval/run_local.py --doctor dummy --patient keyword --judge none` |
| 표준 실험 (비용 추정 → 실행 → 비교 → 뷰어) | `python eval/experiment.py --profile smoke --doctor-endpoint competition` |
| 비용만 미리 보기 | `python eval/experiment.py --profile dev --doctor-endpoint competition --estimate-only` |
| 연습 증례로 평가 | `python eval/run_local.py --cases data/sample_cases` |
| 까다로운 환자로 평가 | `python eval/run_local.py --persona mixed` |
| 두 실행 비교 | `python eval/compare.py --latest 2` |
| 결과 보기 (브라우저) | `python eval/viewer.py` |
| 직접 진료해 보기 | `python eval/play.py` (내가 의사) · `python eval/play.py --role patient` (내가 환자) |
| 지식 베이스 성능 측정 | `python scripts/eval_kb.py` |
| 증례 품질 검사 | `python scripts/check_cases.py` |

| 자동 시험 | `pytest` |

macOS에서는 `진료 테스트.command`를 더블클릭하면 직접 진료 모드가 열립니다.

### 모델 설정
역할별로 다른 모델을 쓸 수 있습니다. `DOCTOR_LLM_*`(의사), `PATIENT_LLM_*`(가상 환자), `JUDGE_LLM_*`(채점)을 따로 지정하고, 지정하지 않으면 공통 `LLM_*`을 씁니다. 모두 OpenAI 호환 접속 방식이라 코드 수정 없이 `.env`만 바꾸면 됩니다. 실험 도구의 `--doctor-endpoint competition`은 `COMPETITION_LLM_*` 설정을 씁니다.

## 대회 규칙 준수

- 추론 코드에서 외부 네트워크 호출 금지 → `scripts/package.py`가 금지된 라이브러리 사용을 검사
- 증례마다 고정 모델을 최소 1회 호출 → 진료 루프에서 보장 (모델이 계속 실패해도 최종 진단 호출을 시도하고, 개발 모드에서는 위반 시 오류)
- 증례 간 정보 공유 금지 → 증례마다 상태·모델 연결을 새로 생성
- 지식 베이스는 CPU에서 동작, GPU는 대회 모델 전용
- 제출 파일 50MB 이하(현재 약 2MB), 모델 가중치·평가 증례 포함 금지 → 패키징 시 자동 검사
- 사용한 모든 데이터·모델·도구의 출처와 라이선스 → [`docs/licenses.md`](docs/licenses.md)

## 현재 상태와 다음 단계
- **기다리는 것**: 대회 참가자 가이드(공식 환경 연결 방식, 진단 형식, 증례당 시간 제한)와 대회 모델 API. 공개되면 `src/doctor_agent/env/official.py`에 연결부만 추가합니다 (지금은 "아직 공개 안 됨" 오류를 내는 자리표시자).
- **아직 측정 안 된 것**: 마지막 언어모델 실험은 v5(제미나이, ClinicalQA 40개 정확도 0.99)입니다. 그 뒤의 변화(지식 베이스 힌트, 코드가 판정하는 검토, 안전 확인 26종, 267증례 세트)는 모델 없이 시험·벤치마크로만 확인했습니다.
- **API 받는 날 할 일** (자세한 순서: [`docs/experiments.md`](docs/experiments.md) "How to run on competition API day"):
  1. `.env`에 `COMPETITION_LLM_BASE_URL`, `COMPETITION_LLM_API_KEY` 입력
  2. 5증례로 연결 확인: `python eval/experiment.py --profile smoke --doctor-endpoint competition` → 호출당 실제 토큰 사용량 확인
  3. 50증례 비교 (지식 베이스 켬/끔): `python eval/experiment.py --profile dev --doctor-endpoint competition --yes --log`
  4. 공식 시간 제한에 맞춰 `AGENT_CASE_TIME_BUDGET_S` 설정, 필요하면 `DOCTOR_LLM_STRUCTURED_OUTPUT` 시험
  5. 결과가 좋으면 전체 267증례(`--profile full`), 그다음 `python scripts/package.py`로 제출 파일 생성 (제출은 하루 1회)
- 제미나이 기준으로 만든 프롬프트는 gpt-oss-20b에서 다시 검증해야 합니다.
